📖 Understanding Request Metrics

Requests Per Minute (RPM)

The rate at which API calls are made to your deployment. Average RPM shows typical load, while Peak RPM indicates maximum burst capacity needed.

Throttling (HTTP 429)

When your request rate exceeds the available capacity, Azure returns HTTP 429 "Too Many Requests" errors. Each throttled request represents a failed API call that may need retry logic.

Throttling Rate Assessment Recommendation
< 1% Healthy PAYG capacity is sufficient
1% - 5% Moderate Approaching limits, monitor closely
> 5% High PTU strongly recommended

📖 Understanding Token Metrics

Tokens Per Minute (TPM)

The rate of token processing, combining both input (prompt) and output (completion) tokens. This is the primary metric for PTU sizing.

Coefficient of Variation (CV)

Standard deviation divided by mean (σ/μ). Measures the relative variability of your workload.

CV Value Workload Type PTU Suitability
< 0.3 Stable/Consistent Excellent for PTU
0.3 - 0.7 Moderate Variability Good if peaks are predictable
> 0.7 Highly Variable May waste PTU capacity

Prompt/Completion Ratio

The split between input and output tokens. Output tokens typically consume more PTU capacity than input tokens, so high completion ratios require more PTU.

📖 Understanding Latency Metrics

Time to First Byte (TTFB)

The time from when a request is sent until the first token of the response is received. Critical for user-perceived responsiveness, especially in chat applications.

Percentile Latencies

  • P50 (Median): 50% of requests are faster than this. Represents typical experience.
  • P95: 95% of requests are faster. Important for SLA definitions.
  • P99: 99% of requests are faster. Captures worst-case scenarios.
Metric Good Acceptable Elevated
P50 TTFB < 500ms 500ms - 1s > 1s
P95 TTFB < 2s 2s - 4s > 4s
P99 TTFB < 4s 4s - 8s > 8s
Variance < 5x 5x - 10x > 10x

📖 Understanding This Report

This guide provides comprehensive explanations of all metrics used in the PTU Advisor analysis. Understanding these metrics will help you make informed decisions about whether Provisioned Throughput Units (PTU) are right for your Foundry deployment.

💡 Tip: PTU provides dedicated capacity with predictable performance and costs, while Pay-As-You-Go (PAYG) offers flexibility with usage-based pricing. The right choice depends on your workload characteristics.

⚖️ PTU vs PAYG: Key Differences

Provisioned Throughput Units (PTU)

Definition: PTU provides reserved, dedicated capacity for Foundry models. You purchase a fixed number of PTUs that guarantee a specific throughput level.
  • Predictable Performance: Guaranteed capacity means consistent latency without throttling
  • Fixed Costs: Monthly commitment, typically more cost-effective at high utilization (>60-70%)
  • Capacity Planning: Requires upfront estimation of throughput needs

Pay-As-You-Go (PAYG)

Definition: Standard deployments use shared capacity with per-token pricing. Pay only for what you use, but may experience throttling.
  • Flexibility: Scale up or down instantly based on demand
  • No Commitment: Pay only for actual token usage
  • Throttling Risk: May receive HTTP 429 errors during peak demand

🎯 The Four Analysis Dimensions

PTU Advisor analyzes your deployment across four key dimensions:

1. Workload Shape

How consistent or variable your token throughput is over time. Stable workloads are ideal for PTU.

2. Capacity Pressure

Whether you're hitting PAYG capacity limits, measured through throttling rate and utilization levels.

3. Latency Sensitivity

Whether you have latency issues and would benefit from PTU's more consistent performance.

4. Load Predictability

Whether your usage follows predictable patterns (daily cycles, business hours, etc.).

📐 PTU Sizing Guidance

If the recommendation is to adopt PTU, here's how to size your deployment:

Required PTU ≈ (Peak TPM × Safety Margin) ÷ PTU Conversion Rate
  • Peak TPM: Use your observed P95 or P99 peak TPM
  • Safety Margin: Typically 1.2x to 1.5x for headroom
  • PTU Conversion Rate: Varies by model (check Azure documentation)
